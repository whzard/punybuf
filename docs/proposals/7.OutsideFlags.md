# Outside flag definitions
Let users define flags that reference flag fields outside of the flag fields.

## Use
Currently, users must write all flags together in a single flag field. This may become unwieldy. It would be better if we allow them to define flags anywhere within the struct and refer back to the flag field.

## Proposed syntax
```pbd
SomeStruct = {
	flags: UInt.{
		flag_1?: String
	}
	flags.flag_2?: U64
	normal_field: String
	flags.flag_3?: U64
	flags.flag_4
}
```
All flags defined inside the flag field are positioned before the flags defined outside. Anonymous flag fields do not need a name, and instead use the type name:
```pbd
SomeStruct = {
	UInt.{
		flag_1?: String
	}
	UInt.flag_2?: U64
	normal_field: String
	UInt.flag_3?: U64
	UInt.flag_4
}
```
> [!todo] Not sure if we should allow this at all. Makes the code kind of confusing

With field ordering, in case the new non-attribute syntax is accepted:
```pbd
SomeStruct = {
	flags: UInt.{
		flag_2?: String
	}
	#     v this is flag #1
	flags.1.flag_1?: U64
	normal_field: String
	flags.flag_3?: U64
	flags.flag_4
}
```

### Alternative syntax:
```pbd
SomeStruct = {
	flags: UInt.{
		flag_1?: String
	}
	flag_2(flags)?: U64
	normal_field: String
	flag_3(flags)?: U64
	flag_4(flags)?
}
```
Clear where it comes from, but a bit heavy.
```pbd
SomeStruct = {
	flags: UInt.{
		flag_1?: String
	}
	flag_2?flags: U64
	normal_field: String
	flag_3?flags: U64
	flag_4?flags
}
```
Looks strange, but also fairly acceptable. In case of anonymous flags maybe remove the flag field reference entirely (although that might be even more confusing, especially if people forget that `?` there)
```pbd
SomeStruct = {
	flags: UInt.{
		flag_1?: String
	}
	flag_2: flags?U64
	normal_field: String
	flag_3: flags?U64
	flag_4: flags?
}
```
Has better parity with how flags appear in the generated code, but makes it a bit confusing on what is the type vs the disposition.
