# Proposal: Streams
Streams would allow a command to return its value multiple times, thereby enabling a continuous stream of values.

## Use
### Progressively receiving data
Streams can be useful for displaying data before it hits the network, for example in a command like:
```pbd
getTransactions: {
	payment_method_id: U64
} -> Array<Transaction>
```
Using the current codegen, there is no way to access any transactions before deserializing the enitre array.

A workaround may be to use two commands:
```pbd
startTransactionStream: {
	payment_method_id: U64
} -> StreamDetails {
	id: U64
	count: UInt
}
transaction: {
	id: U64
	transaction: Transaction
} -> Void
```
This makes us pass the `id` or some value identifying the stream along with every chunk, which is a waste since ideally we'd "respond" to the command just using its `seq_id`. The receiver of the `transaction` commands already knows the type, so we're wasting bandwidth by including an extra sequence number in our connection. A benefit of this approach is that we have separate units responsible for starting the stream and receiving its contents, which leads to a possibility of a more granular protocol evolution.

Another alternative is to special-case the `Array` to be able to be received as a stream by the codegen. It's unclear how it would look like in practice, since we'd have to keep track of the amount of things received over the network. This still holds up the bandwidth and prevents any other commands or responses from being received while the response is streamed. As a plus side, it does not require any modification from the sender side. However, it wouldn't really be possible if the return type isn't a simple `Array`, but contains some other data.
### Streaming updates / events
Usually, any events or updates can just use commands. However, we sometimes would like to pick and choose which events we're supposed to receive. While this is still possible with commands, it ends up a bit clunky with, again, having to pass an `id` argument everywhere:
```pbd
subscribeToEvents: {
	scope: String
} -> Void
event: {
	scope: String
	event: Event
} -> Void
```
Encoding a `String` every time can be worked around by using stream identifiers, but at this point, again, we're wasting space and doing the protocol's job for it.

Another workaround is to use something like long polling:
```pbd
pollNewEvent: {
	scope: String
} -> Event
```
With the implication that this command may take a long time to receive a response. This is a lot better, except that the receiver must keep sending the `pollNewEvent` command. Moreover, without event sequence tracking (which is no better than a stream ID), the receiver might miss some events in case it's too slow.

Again, this is doing the protocol's job for it.
## Proposed syntax
Introduce a new command type (similarly to how void-commands are treated as special), a **stream-command**. In the syntax, it would look like this:
```pbd
streamEvents: {
	scope: String
} -> Stream<Data, Event> ![SomeError]
```

The stream definition, like `Void`, would use a special attribute:
```pbd
@stream
Stream<InitialData, Element> = InitialData
```

The stream type is special because it would support a second definition:
```pbd
@stream
Stream<Element> = Void
```
Which is like having a default argument for the initial data.

The command error enum will contain a "stream end" pseudovariant `1` (in addition to the "unknown error" pseudovariant `0`), that specifies that the stream is over.

## Proposed Binary Format
A stream command is sent like any other normal command. It has a `seq` number, which we'll refer to as `stream_seq`.

The (de)serialization of the stream response is as follows:
1. If the stream contains initial data (`InitialData`), the first frame with type `RESPONSE_RETURN` and its `seq` set to `stream_seq` must be (de)serialized as the `InitialData` type and the `seq` association must not be dropped. Otherwise, this step is skipped.
2. For every frame with type `RESPONSE_RETURN` and `seq = stream_seq`, it must be (de)serialized as `Element`. The `seq` association must not be dropped.
3. The frame with type `RESPONSE_ERROR` and `seq = stream_seq` means that the stream is over. It must be (de)serialized as the command error enum, and must contain a value of "stream end" if and only if the stream ended successfully.

The main way of supporting streams is just allowing mulitple responses to a command, with optionally special casing the first one (containing initial data) and special casing an error enum variant to mean "stream ended successfully"
