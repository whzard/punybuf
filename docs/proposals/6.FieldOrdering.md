# Field numeration
Let users lay out fields in any order without breaking binary compatibility

## Use
Currently, users must write all fields in the order they appear on the wire, so extensions must always be added to the flags field and at the bottom, which is inflexible. Propose either a syntax or an attribute to reorder fields.

## Proposed syntax
```pbd
SomeStruct = {
	2.field_two: UInt
	1.field_one: String
	3.field_three: U8
	field_four: U64
}
# or
SomeStruct = {
	@at(2) field_two: UInt
	@at(1) field_one: String
	@at(3) field_three: U8
	field_four: U64
}
```

The syntax is either: `<number>` `.` before a field name or anonymous flags, or an attribute `@at(n)` on the field. Field numbers begin with 1.

Benefits of using `@at` is that it's easier to integrate without introducing new syntax, while a benefit of `n.` is that it combines better with the outside flag definition syntax.

Fields are ordered based on their assigned number or on their position. Gaps inside structures are not permitted:
```pbd
SomeStruct = {
	normal_field: UInt
	@at(3) gap: String
#          ~~~ gap inside a structure, missing field 2
}
```
Struct definitions may combine both numbered and unnumbered fields in any way:
```pbd
Example = {
	1.numbered: Stirng
	2.also_numbered: UInt
	not_numbered: String
	3.numbered_again: UInt
}
```
In this case, the `not_numbered` field will get the number 4.
```pbd
Example = {
	normal_field: String
	another_field: UInt
	4.numbered_field: F64
	unnumbered: U32
}
```
In this case, the layout will be `{String} {UInt} {U32} {F64}`.

The compiler must first assign positions to all numbered fields, before filling the remaining slots with unnumbered fields. If there are any slots remaining, this is an error.

Changing a field number is always a backwards incompatible change.

Adding a field number to a field is a backwards incompatible change in case that field number doesn't already correspond to that field number.

Removing a field number from a field is a backwards incompatible change if the field will change its position after removal.

Fields marked with `@extension_flags` must have the last position in the struct regardless where they appear in the struct definition.

Flag fields may also be numbered:
```pbd
SomeStruct = {
	flags: UInt.{
		flag_1?: String
		@extension @at(3) flag_3?: String
		flag_2?
	}
}
```
Optionally, propose an extension for the `@extension` attribute:
```pbd
SomeStruct = {
	flags: UInt.{
		flag_1?: String
		@extension(3) flag_3?: String
		flag_2?
	}
}
```
Which would be more consise.

Positions of flags are calculated the same way positions of fields are. Numbered extension flags must leave enough room for normal flags, and gaps are still not allowed (as that might break the binary format).

## Proposed IR changes
To allow for a more intuitive structure generation, each struct object may contain an optional `"original_position"` property representing a number of the original field position, so the codegen may reorder the generated fields.

This requires a minor version bump.
